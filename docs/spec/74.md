## §1 — Tab placement and structure

- `components/projects/DueDiligenceTab.tsx` — new `TabsTrigger value="diligence"` / `TabsContent`, added **first** in `ProjectsWorkspace.tsx`'s tab list (Due Diligence | Budget | Scopes | Schedule | Draws | Exit pack). The default *active* tab on load is left as `budget` — the issue asked for Due Diligence to be first in order ("it is the entry assessment"), not that it also change the existing default landing tab, so that behavior is unchanged for every existing user.
- The tab reuses the workspace's existing "current property" context — the selected budget (`detail`/`selectedId` state already in `ProjectsWorkspace.tsx`) — the same pattern `ScopesTab.tsx` already uses. There is no separate "property" selector in this workspace; a budget *is* the per-property context here.

## §2 — Gating (paid-member hard requirement)

Reused the existing Clerk + Supabase tier pattern (`lib/tier/server.ts`) rather than inventing a new backend capability that this repo can't verify server-side:

- `app/projects/page.tsx` already calls `requireCapability('get_rehab_budget')` to gate the whole page — that capability's tier floor was confirmed (via `components/deed-home/LandingSections.tsx` `PLANS`) to already be **Pro Plus** ("Construction and property management" is a Pro Plus line item). So every user who reaches `ProjectsWorkspace` today is already Pro Plus or Enterprise.
- Added `tierAtLeast(tierId, minTierId)` to `lib/tier/server.ts` — a small tier-rank comparator (`free < investor < pro < proplus < enterprise`). `page.tsx` now computes `dueDiligenceAllowed = tierAtLeast(check.tierId, 'proplus')` from the **same** `requireCapability` call already made for the page (no extra RPC round-trip) and passes it down as a prop.
- This makes Due Diligence's gate independent of `get_rehab_budget`'s tier floor: if that capability's required tier is ever loosened, Due Diligence stays Pro Plus-only on its own, deliberately — it doesn't ride on a capability whose meaning could drift.
- **Defense in depth**: `app/api/projects/diligence/route.ts` independently re-checks `tierAtLeast(check.tierId, 'proplus')` server-side before returning any capture data — a signed-in Investor/Pro user hitting the endpoint directly gets a 402, not just a hidden tab client-side.
- Free/lower-tier UI: `components/projects/DueDiligenceLocked.tsx`, an inline upgrade panel (not a full-page takeover, since the rest of Projects is already reachable at this tier) styled identically to `ProjectsLocked.tsx`/`D4DLocked.tsx` — badge, lock icon, CTA to `/subscribe?tier=proplus`, "you are on X today" line.

## §3 — Data: `app/api/projects/diligence/route.ts`

- `GET ?budgetId=<uuid>` — mirrors the existing `app/api/projects/*` route pattern: `requireCapability` + tier check → 402; UUID regex validation → 400; `callerOwnsBudget` ownership check (added `projectIdForBudget` to `lib/projects/server.ts` alongside the existing `ownerEmailForBudget`/`budgetIdForLine`/`budgetIdForScope` helpers) → 404 if not owned.
- Resolves `cm_budgets.project_id` for the budget, then reads the most recent `gev_captures` row for that `project_id`.
- **Caveat, stated plainly**: `gev_captures` is written by the capture+assessment pipeline described in the companion `cli-anything-biddeed#20214` issue, which is out of scope for this repo and had not shipped as of this session — the table's real schema, and whether budgets actually carry a populated `project_id` today, could not be verified from this repo (no SQL migrations live here; schema lives in Supabase, owned elsewhere). The route is written defensively: any error reading `gev_captures` (including "relation does not exist") or a null `project_id` is treated as "no capture" (`{ capture: null }`), not a 500 — that's the true, expected state before the pipeline has run, not an error condition. The column list in the `.select(...)` (`video_url`, `framing`, `capture_status`, `captured_at`, `assessment`, `mapillary_image_id`, `mapillary_captured_at`, `mapillary_thumb_url`, `street_view_url`, `street_view_captured_at`) and the `assessment` JSON shape (`roof`, `structure`, `lot`, `visible_defects[]`, `imagery_stale`) in `components/projects/types.ts` (`GevCapture`/`GevAssessment`) are the **contract this UI expects** — if the pipeline lands with different column/key names, either side needs a one-line adjustment to match.

## §4 — UI: `components/projects/DueDiligenceTab.tsx`

- Loading / error / empty (`ComingSoonPanel`, title "Aerial assessment not captured yet") / populated states, following the same state-machine shape as `ScopesTab.tsx`.
- Populated view: two side-by-side cards (aerial video; street-level imagery) plus a full-width assessment card below.
- Aerial video: plain `<video controls playsInline>` — there was no pre-existing video-embed pattern anywhere in this repo to mirror, confirmed by an empty-result grep.
- Assessment card: roof / structure / lot / visible-defects (`<dl>` grid), **and the imagery-stale flag as a `Badge variant="destructive"` in the card header, rendered whenever `assessment.imagery_stale` is true, never inside a collapsed/hover-only element** — the explicit product rule from #20212 in the issue.

## §5 — MapillaryJS viewer

- `components/projects/MapillaryViewer.tsx` — new client component, structured like the existing `D4DMap.tsx`/`AuctionMap.tsx` Mapbox components (env-token-gated, ref-based `useEffect` init/teardown). Added `mapillary-js@4.1.2` to `package.json` (ships its own `.d.ts`, no separate `@types` package needed). `npx tsc --noEmit` is clean.
- Reads `capture.mapillary_image_id` and calls `new Viewer({ accessToken, container, imageId })` exactly as specified in the issue comment.
- Shows `captured_at` next to the viewer: "Street-level imagery: <date>".
- **Fallback rule honored** ("never an empty viewer"): when `mapillary_image_id` is null, falls back to `capture.street_view_url` + `street_view_captured_at` with an explicit "No Mapillary coverage near this parcel — showing the Street View capture instead" message; only if *neither* exists does it show a plain "not available yet" line.
- When the token itself is unset, the viewer renders a "Mapillary token not configured" placeholder instead of crashing — verified in the browser (see §7, mapillary-fallback screenshot).
