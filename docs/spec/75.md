## §0 — The data ceiling (read first)

This sandbox's environment carried `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`,
`SUPABASE_ANON_KEY`, and `SUPABASE_ACCESS_TOKEN` as **declared but empty** env vars — `env` listed
the names, but `${#VAR}` was 0 for every one of them. `NEXT_PUBLIC_MAPBOX_TOKEN` was the only
real secret present (92 chars, confirmed working — tiles render live in every screenshot below).

Consequences, stated plainly:
- Every Supabase-backed API route in this PR (`/api/heatmap/scorecard`, `/api/heatmap/premium`,
  `/api/analytics/event`) is **code-complete and follows this repo's existing patterns exactly**
  (`getRetryingSupabaseClient()`, `requireCapability()`, the pagination convention from
  `app/api/auctions/map/route.ts`) but has never executed a real query against
  `mocerqjnksmhcjzxrewo`. Live screenshots below show the honest failure mode — a "Could not load
  the scorecard for this county" message and a "Live auction pins are temporarily unavailable"
  banner — because the client throws on construction (`supabaseUrl is required`), not because the
  route logic is wrong.
- `supabase/migrations/20260910120000_heatmap_funnel_events.sql` has **not been applied to any
  database**. Nothing has ever been written to `heatmap_funnel_events`. There is no sample query
  result in this PR because there is no data to query — showing a fabricated one would violate the
  issue's own "never fabricate" rule, so I did not.
- The `view_premium_heatmap_layers` capability added to `lib/tier/server.ts` has no corresponding
  row in the Supabase-side `user_has_capability` RPC data. Until that's registered (out of scope
  here — the issue lists "Supabase CI registrations" as proposal-only elsewhere), every caller gets
  `allowed: false`, which is the correct fail-closed behavior for a paywall and is what the
  paid-gate screenshot shows.

None of this is a workaround or a shortcut — it's the actual, current state, and it's why sections
C1 and D1–D5 of the issue's own checklist are marked **NOT DONE** above rather than glossed over.

## §2 — Free KPI layer + gating (B2)

`lib/heatmap/config.ts` is the single layer registry (`KPI_LAYERS`), read by every surface —
server routes, `LayerPanel`, `HomepageMapInteractive`. `market_direction` (median home value,
county) is `tier: 'free'` and always interactive, no account required. `median_income` is
`tier: 'signup'`. `foreclosure_density` is `tier: 'paid'`. `zhvi_yoy`, `inventory`, `dom`,
`price_cut_pct`, `forecast_1yr` are marked `hasData: false` with a `noDataReason` — no Zillow ETL
feeds this repo (confirmed: `grep -rli "zillow|zhvi"` across the repo returns nothing before this
PR). Locked/no-data layers stay listed, dimmed, with a lock icon — never hidden.

Signed-in state is resolved **server-side** in `app/maps/page.tsx` via
`requireCapability('view_premium_heatmap_layers')` (`userId != null` → signed in,
`allowed` → paid-entitled), not via a client Clerk hook — `ConditionalClerkProvider` no-ops when
Clerk's env pair is absent (confirmed true in this repo today, `middleware.ts` lines ~14–21), and
calling `useUser()`/`useAuth()` outside a mounted `ClerkProvider` throws. This mirrors the existing
`authEnabled` prop pattern in `components/shell/AppSidebar.tsx`.

## §3 — Pin legibility over the choropleth (B3)

`components/heatmap/HeatmapMap.tsx`: the county fill layer (`fill-opacity: 0.5`, data-driven color
via `lib/heatmap/colorScales.ts`) is added first; the auction pin cluster/point layers are added
with no `beforeId`, i.e. after every other layer in that render pass — topmost, always. Pins use a
solid `#0f172a` fill with a 2.5–3px white (`#ffffff`) stroke halo, one consistent color regardless
of `sale_type`, deliberately — a color-coded-by-type pin would have competed with the diverging
value/density ramps for the same visual channel. Verified visually in
`docs/spec/75-assets/maps-desktop-scorecard-selected.png`: the fill is a visible but soft
lavender/purple gradient, county outlines and the blue selection outline both read clearly on top
of it. **Pin rendering itself was not visually verified** — see §6, this sandbox had no live
`multi_county_auctions` rows to plot.

## §4 — Source + vintage captions (B4, C4)

Every KPI value in `ScorecardPanel.tsx` and `HomepageMapInteractive.tsx` renders
`{layer.source} · {layer.vintage}` next to the number — e.g. "U.S. Census Bureau ACS 5-Year
Estimates, table B25077 · ACS 2020-2024". No number renders without this pairing. Verified in every
`/maps` screenshot.

## §5 — Scorecard, deterministic top-parcel rule, honest empty state (B5)

`lib/heatmap/topParcel.ts` ranks candidate auction rows by the existing Shapira Formula
recommendation (`lib/scoring.ts`'s `getRecommendation` — BID > REVIEW > SKIP > UNKNOWN, the same
engine `/radar` uses), tie-broken by soonest `auction_date`. Same input rows always produce the
same output — no randomness. `app/api/heatmap/scorecard/route.ts` also implements the "zero live
auctions → offer the nearest county with inventory, never invent one" rule from the issue's risk
list: on an empty result it queries the rest of the state, ranks by count, and surfaces the
highest-inventory alternative with a "jump there" affordance
(`ScorecardPanel.tsx`'s `nearest_with_inventory` branch). **Not exercised against real data** in
this session — see §6.

## §7 — Shareable URL state (B6, and the "beat Reventure" requirement)

`lib/heatmap/url-state.ts` encodes `layer` / `gran` / `sel` into the query string;
`MapsPageClient.tsx` calls `router.replace()` on every state change. Every param is validated
against a closed set on parse (`parseHeatmapSearchParams`), not trusted as free text. The homepage
teaser CTA builds the same params so a click into `/maps` carries geography + KPI + selection.
Verified: `docs/spec/75-assets/maps-shared-link-reproduces-state.png` loads cold from a URL with
`sel=009` and shows Brevard County pre-selected, no click needed. Reventure does not do this
(issue's own grounding note, not re-verified independently here).

## §9 — Lazy-load + SSR preview (B8)

`HomepageMapModule.tsx` is a client component but its first-paint content (county count, real
statewide median home value, source/vintage caption) comes from a static import
(`lib/heatmap/data/fl-county-acs-2024.json`) — no client fetch needed, so it's present even before
hydration. The actual Mapbox bundle (`HomepageMapInteractive`, `next/dynamic(..., { ssr: false })`)
only mounts once an `IntersectionObserver` reports the section within 200px of the viewport.
**Not benchmarked against the <2s budget in this session** — no realistic network throttling was
applied; local dev load was visually near-instant with a warm cache, which is not evidence for a
cold-cache/throttled mobile number.

## §10 — Funnel events (B9)

`lib/heatmap/config.ts` `FUNNEL_EVENTS` is the closed set (15 names, exactly the ones the issue
lists plus the 5 Amendment-2 homepage events). `lib/analytics/track.ts`'s `trackHeatmapEvent()` is
called from every interaction point: layer switch, gate shown (both kinds), county selection,
SIGNAL$ CTA click, homepage view/interact/teaser-click/to-maps-click, `heatmap_view` on `/maps`
mount. `app/api/analytics/event/route.ts` is deliberately fail-open — a 202 on bad input, a missing
table, or a Supabase error alike, because a tracking call must never be able to break the map (this
was tested: the route never once caused a client-visible error during the whole verification pass,
even though every insert failed against the absent table).

**No event has ever actually landed in a database** — see §0. The weekly rollup view
(`public.heatmap_funnel_weekly` in the same migration file) has never been queried against real
rows. This PR does not claim a sample query result because none exists yet; running
`select * from public.heatmap_funnel_weekly order by week_start desc limit 50;` after the migration
is applied and the funnel has real traffic is the next session's job, not this one's.

## §13 — ACS / Census Reporter data layer

Real data, not a placeholder. Pulled 2026-09-10 via `api.censusreporter.org`
(`B25077` median home value, `B19013` median household income, `B01003` population; release
`acs2024_5yr`, "ACS 2024 5-year", years "2020-2024") for all 67 Florida counties plus a statewide
aggregate. Cross-checked against the issue's own Viera East example: this pull's Florida statewide
figures ($359,000 median home value, $74,568 median household income) match the issue body's cited
comparison values exactly, confirming the same release. County boundaries
(`public/data/heatmap/fl-counties.geojson`) are the real Census-TIGER-derived FL county polygons
(67 features, GEO_ID/FIPS-keyed), sourced from `plotly/datasets` (a standard, widely-used
redistribution of Census cartographic boundary files), not fabricated or hand-drawn. Both files are
duplicated under `public/data/heatmap/` (client fetch) and `lib/heatmap/data/` (server import,
required because `resolveJsonModule` + RSC bundling don't cleanly support importing across that
boundary) — a note is embedded in the `lib/` copy's `_note` field flagging the two must stay in
sync by hand.

ZIP-level (ZCTA5) ACS data was explicitly **not** pulled for this pass — scoped out to keep this
session bounded; the granularity gate UI is fully functional (see §2), it just has no real ZIP
figures behind it yet, same documented-gap treatment as the Zillow KPIs.
