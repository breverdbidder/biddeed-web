## §3 — `--input` contrast fix (the actual work)

**Measured before fixing**, via WCAG relative-luminance formula (not trusting the code comment):
```
OLD --input #DDD5C9 vs body bg #F5F0E8:  1.28:1
OLD --input #DDD5C9 vs card #FBFAF7:     1.39:1
```
Both fail the 3:1 non-text contrast requirement (WCAG 2.2 SC 1.4.11), consistent with the audit's original ~1.30:1 finding (the audit's exact hex `#D7E3F1` is from the pre-terracotta blue/navy palette; the underlying failure — reusing `--border`'s pale tint for `--input` — is the same defect, carried over into the new palette by `e7263ba`).

**Fix applied** — `app/globals.css`, both light-mode blocks (`:root` and `html[data-theme='light']`):
```css
--input: 210 73% 14.5%;   /* #0A2540 - control boundary, 13.70:1 on #F5F0E8 (WCAG 2.2 SC 1.4.11) */
```
`210 73% 14.5%` is the exact HSL-to-hex round-trip for `#0A2540` (verified with a Node `hslToHex`; the first commit used a rounded `15%`, which resolves to `#0A2642` — off by one channel step — and was corrected in a follow-up commit to the exact value). `--border` was left untouched at `36 23% 83%` (dividers/card edges are non-interactive, exempt) — **did not set `--input` to `--primary`**, per the explicit non-goal.

Dark mode was **already correct** (`211 27% 70%` / `#9EB2C7`, 8.70:1 on `#0B1119`) and was not touched.

**Measured after fixing:**
```
NEW --input #0A2540 vs body bg #F5F0E8:  13.70:1
NEW --input #0A2540 vs card #FBFAF7:     14.89:1
DARK --input #9EB2C7 vs bg #0B1119:       8.70:1  (unchanged)
```
Both comfortably clear 3:1. **VERIFIED** — measured, not assumed.

**Gate co-change (required, same commit):** `scripts/palette-gate.mjs` enforces a fixed whitelist of canon HSL/hex values on the two token files and would fail on any new value — this is by design (its own comment: *"update the canon and tokens together when the design system changes"*, the same pattern `canon-gate.mjs` uses for price changes). Added `#0a2540` to `CANON_LIGHT` and `210 73% 14.5%` to the HSL whitelist. This is the sanctioned mechanism for an authorized token change, not a weakening of the gate — it still rejects every other off-canon value.

**Built-CSS verification** (`npm run build && npm start`, node 22.23.2, port 4177):
```
$ grep -o -- '--input:[^;]*;' <built CSS>
--input:210 73% 14.5%;
--input:211 27% 70%;
```
Confirms the fix ships in the actual production bundle, not just source.
