## Root cause (Finding 1) — `--input` is correct, six call sites never asked for it

15.54:1) — confirmed via `getComputedStyle(document.documentElement).getPropertyValue('--input')`

`input: 'hsl(var(--input))'`. The shared `<Button variant="outline">` primitive correctly emits

## Root cause (Finding 2) — `bg-primary-hover` was never a registered Tailwind color

`components/auctions/AuctionMap.tsx`'s "Cluster size" legend renders three swatches, the middle
one styled `bg-primary-hover ... text-primary-foreground`. Live DOM inspection
(`getComputedStyle`) showed:

```
swatch 1 (bg-primary):        backgroundColor: rgb(0, 94, 184)   [correct]
swatch 2 (bg-primary-hover):  backgroundColor: rgba(0, 0, 0, 0)  [TRANSPARENT]
swatch 3 (bg-muted-foreground): backgroundColor: rgb(10, 37, 64) [correct]
```

`tailwind.config.ts`'s `colors.primary` object only declared `DEFAULT` and `foreground` — no
`hover` key — so `bg-primary-hover` matched no generated Tailwind utility and compiled to
nothing. The swatch's own background silently fell through to transparent, and the walk-up-
parents contrast reader landed on the legend box's `bg-card/90` (near-white) backdrop. White text
(`text-primary-foreground`, `#ffffff`) on a transparent-then-near-white background: 1.00:1.

Same failure mode the issue asked to be swept for ("something set a foreground to white without
checking the surface under it") — except here the "surface" itself silently disappeared, not the
foreground.

Five call sites referenced `bg-primary-hover` / `hover:bg-primary-hover` /
`hover:text-primary-hover` and were all silently inert for the same reason
(`ConditionalClerkProvider.tsx` ×3, `DiscoveryPage.tsx` ×1, `AuctionMap.tsx` ×1) — the fix
restores all five, not just the measured one.

**Diff:**

```diff
  primary: {
    DEFAULT: 'hsl(var(--primary))',
-   foreground: 'hsl(var(--primary-foreground))'
+   foreground: 'hsl(var(--primary-foreground))',
+   hover: 'hsl(var(--primary-hover))'
  },
```

**AFTER (post-deploy):** 0 instances of the `n`-span failure; `badTextCount: 0` overall.

### Adjacent finding fixed in the same pass, same failure class: `lib/scoring.ts`

Not cited in the issue's specific evidence, but the same "foreground set without checking the
surface" pattern, found while tracing the badge/status-banner sweep (§3): `AuctionTable.tsx` and
`AuctionSpreadsheet.tsx` render a recommendation pill with `text-white` hardcoded and a *dynamic*
`backgroundColor: score.color`. For `SKIP` (ratio < 60%), `score.color` is `C.border`
(`#D7E3F1`, light) — white text on it measures 1.30:1, effectively invisible. Fixed by adding
`ScoringResult.textColor` and picking dark ink for the light fill, matching the pre-existing
`.grade-E`/`.grade-X`/`.grade-Z` convention (`app/globals.css:182-184`) that already does exactly
this for the same token.

## §3 — Badge/pill text at 1.38:1

BEFORE (from the same run): 84 instances of `rgb(0,74,146) on rgb(0,94,184) | ratio=1.38` —
`#004A92` foreground (the `--primary-hover` token) on the *raw, un-composited* channel value of
`rgba(0,94,184,0.1)` (`bg-primary/10`).

## Root cause (Finding 3) — translucent tint + solid-hue text, measured without compositing

`app/globals.css:382-384` already has a compensating rule:

```css
.bg-secondary .text-primary, .bg-muted .text-primary, .bg-secondary.text-primary, .bg-muted.text-primary,
[class*="bg-primary/"] .text-primary, [class*="bg-primary/"].text-primary,
[class*="bg-secondary/"] .text-primary, [class*="bg-muted/"] .text-primary { color: hsl(var(--primary-hover)); }
```

— written against a *composited* mental model ("#005EB8 on #E6F0FA is 4.31:1, so text on the tint
takes the darker hover blue instead, 5.97:1 on the tint / 6.67:1 on white"). That's correct for
what a human eye sees: a 10%-alpha blue tint over a white card reads as pale blue, and dark navy
text on pale blue is fine. It is **not** correct for a contrast reader that takes the element's own
`rgba(0,94,184,0.1)` `background-color` at face value and never composites it onto what's behind —
which is what a plain `getComputedStyle` + luminance-formula tool does by default, and (confirmed
by matching the issue's exact `1.38` and `1.00` ratios) is what measured this issue. Against the
raw, uncomposited channel values, `#004A92` text on `rgb(0,94,184)` background is 1.38:1 — a real
number a real tool reports, even though the human-visible rendering passes.

Fix: replace the translucent tint (`bg-primary/10`, `bg-foreground/10`) with the existing
**opaque** `--secondary` token everywhere this pattern renders text — same visual "pale tint"
result, but now `alpha = 1` so there is no composited-vs-raw discrepancy for any measurement tool
to catch, current or future. Applied to 8 sites: `app/counties/page.tsx` ("Gold Standard"),
`components/deed-home/LandingSections.tsx` ("Most chosen"), `components/pricing/PricingTiers.tsx`
("Most chosen"), `components/deed-home/AuctionCards.tsx` (sale-type pill), `components/auctions/
AuctionDetail.tsx` (`typeBadge()`, both the primary and foreground branches), `components/
auctions/AuctionsLayout.tsx` (day-filter chip), `components/auctions/AuctionSidebarList.tsx`
(selected-row state), `components/auctions/AuctionMap.tsx` (fetch-error and truncation status
banners — the latter is also where the issue's ink-on-ink evidence, `rgb(26,26,26) on
rgb(26,26,26)`, 18 instances, "Showing 2,064 of 2,883 matching auctions on the map." — came from;
same `bg-foreground/10 text-foreground` shape, same fix).

**AFTER (post-deploy):** 0 instances of the 1.38:1 pair; `badTextCount: 0` overall (includes the
18 ink-on-ink and 4 white-on-white instances from the same run — all zero).
