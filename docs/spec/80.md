# 80 — Privacy containment: hide and clear client-side Recent chat history

Repo: `breverdbidder/biddeed-web`. Session: 2026-09-10. Delivered as a branch for owner review (not committed to main, not merged), per the issue's explicit delivery-shape instruction.

Scope, per the issue: **this repo's client only**. The Worker/API containment and the permanent verified-owner model are specified in `breverdbidder/cli-anything-biddeed#20226` and are out of scope here.

## Flag

`NEXT_PUBLIC_CHAT_HISTORY_CONTAINMENT` — read by `lib/deed/chatHistoryContainment.ts`'s `chatHistoryContainmentEnabled()`.

- **Default: ON** (containment active) for any value other than the literal string `'false'`, including unset. A privacy boundary should fail closed.
- **To reverse**: set `NEXT_PUBLIC_CHAT_HISTORY_CONTAINMENT=false`, or delete the four call sites of `chatHistoryContainmentEnabled()` once the permanent boundary in #20226 ships (`lib/deed/threads.ts` ×2, `components/shell/AppSidebar.tsx` ×1, `ChatHistoryContainmentGate.tsx`/`ChatHistoryContainmentAuthWatcher.tsx` ×1 each).
- Documented in `.env.example`.
- Must be `NEXT_PUBLIC_`-prefixed: every read site (`lib/deed/threads.ts`, `AppSidebar.tsx`, the two new gate components) runs in the browser, and only `NEXT_PUBLIC_*` vars are inlined into the client bundle by Next.js.

## §1 — Hiding "Recent" (`components/shell/AppSidebar.tsx`)

`useRecentThreads()` now returns `[]` without ever calling `loadThreads()` or `subscribeThreads()` when containment is active — the group is hidden by the existing `recent.length > 0 ? … : null` render guard, and no localStorage read is even attempted (belt), on top of `loadThreads()` itself also returning `[]` under containment (suspenders, see §2). `AppSidebar` is the single sidebar component for every route including `/projects` — there is no separate mobile sidebar; `components/ui/sidebar.tsx` swaps the same component into a Radix `Sheet` under the mobile breakpoint. Confirmed live: `/projects` at desktop and at 390×844 (mobile Sheet) both render the sidebar (`Workspace`/`New chat` present) with no `Recent` group.

## §2 — Disabling reload/history reads (`lib/deed/threads.ts`)

`loadThreads()` and `saveThread()` short-circuit under containment:
- `loadThreads()` returns `[]` — `loadThread(id)` is defined in terms of `loadThreads()`, so reload via `/?c=<id>` degrades to "not found" (a fresh new-chat state) rather than reading anything back.
- `saveThread()` no-ops — no new thread is ever written to `localStorage` while containment is active, so the home surface's previously-persisted chat degrades to the same non-persistent behavior the side-panel chat (`useDeedChat.ts`) already had. This is deliberate: the issue's acceptance criteria imply no chat history should survive a reload during containment, not just that old history is hidden.
- `deleteThread()`/`clearThreads()` are left fully functional — removing data is never a containment violation, and `clearThreads()` is the primitive the two gate components below call.

There is no server-side thread list/search API in this repo to begin with (confirmed by code search) — the "no saved-chat list/search network calls fire" acceptance criterion was already true structurally; this change makes the client-side read path (which the sidebar/reload rely on) inert as well.

## §3 — Wipe on load and on auth transitions

Two small client components, both `return null`:

- **`components/shell/ChatHistoryContainmentGate.tsx`** — calls `clearThreads()` once on mount. Mounted unconditionally in `app/layout.tsx` (inside `ThemeProvider`, before `ConditionalClerkProvider`), so it runs on every route on every load regardless of whether Clerk is configured.
- **`components/shell/ChatHistoryContainmentAuthWatcher.tsx`** — uses Clerk's `useUser()` to track `user?.id`, calling `clearThreads()` again whenever that id changes after the first resolved value (covers sign-in `null→id`, sign-out `id→null`, and account switch `idA→idB`). Mounted inside the active `<ClerkProvider>` branch in `components/ConditionalClerkProvider.tsx` — it must live there because `useUser()` throws outside a `ClerkProvider`, and this app's Clerk provider is itself conditional on host/env (see that file's existing gating).

Only one localStorage key exists for saved threads (`biddeed.deed.threads.v1`, confirmed via `git log -p` — no prior key name was ever used), and no IndexedDB/sessionStorage chat-history keys exist anywhere in this repo (confirmed by search). `clearThreads()` removes exactly that key.

**Scoping decision, stated explicitly**: `lib/deed/chatIdentity.ts`'s `bd_chat_token`/`bd_chat_email` localStorage keys are a separate concern (a per-visitor identity token for the Worker's own attribution, shared by key-name convention with the Worker's `/chat` page) — not "saved thread" data per the issue's own wording, and not touched here. If cross-account identity leakage through that token turns out to matter, it belongs in the Worker/API containment lane (#20226), since the Worker is what actually consumes it.

## §4 — Verification

Ran locally against `next dev` (Turbopack) with Playwright (chromium), scoped to this change — not run against staging/production, since this branch is not deployed anywhere:

1. **Clean browser** (`/projects`, desktop): no `Recent` text node renders; `localStorage['biddeed.deed.threads.v1']` stays `null` after load. **PASS**.
2. **Clean browser, mobile Sheet** (`/projects` at 390×844, sidebar trigger opened): no `Recent` group. **PASS**. Sanity-checked separately that the sidebar itself (`Workspace`, `New chat`) does render there, so this isn't a false pass from a hidden/gated page.
3. **Legacy stored thread data**: seeded `localStorage['biddeed.deed.threads.v1']` with a fake thread containing the string `"secret past chat"`, reloaded `/`. After reload: the key is `null`, no `Recent` group, and the seeded title text is absent from the DOM. **PASS**.
4. **Sending a message on `/` (home)**: composer send → after the turn settles, `localStorage['biddeed.deed.threads.v1']` is still `null` (chat itself works — the turn renders — it just isn't persisted). **PASS**.
5. **Reversibility check**: restarted `next dev` with `NEXT_PUBLIC_CHAT_HISTORY_CONTAINMENT=false`, repeated the seeded-storage reload. With the flag off, the seeded thread's title renders in a visible `Recent` group and the storage key survives the reload — i.e., flipping the flag restores the exact pre-containment behavior. **PASS**. This is the "trivially reversible" requirement demonstrated, not just asserted.
6. `npx tsc --noEmit`: clean.

**Not verified, and why**: sign-in/sign-out/account-switch clearing (`ChatHistoryContainmentAuthWatcher`) could not be exercised live — this sandbox has no `CLERK_SECRET_KEY`/`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` pair configured, so `ConditionalClerkProvider` never mounts a real `ClerkProvider` and the watcher never mounts either (by design — it depends on Clerk being active, mirroring how the rest of this app gates Clerk). The logic was verified by static reasoning instead: `useUser()`'s `user?.id` is tracked in a ref; the first resolved value after `isLoaded` is recorded without clearing (the app-load gate already covered first render); every subsequent change — `null↔id` or `idA↔idB` — calls `clearThreads()`. `npx tsc --noEmit` passes with the Clerk types in scope. A session with real Clerk test-instance credentials should exercise this against a deployed preview before the owner merges.
