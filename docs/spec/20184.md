## §2 — error.tsx / global-error.tsx / not-found.tsx

```
$ ls app/error.tsx app/global-error.tsx app/not-found.tsx
app/error.tsx
app/global-error.tsx
app/not-found.tsx
```

Retry logic lives once, in `lib/reboot-retry.ts` (`useRebootAwareRetry` hook), used by both
`app/error.tsx` and `app/global-error.tsx` — factored into one place rather than copy-pasted
because both boundaries need byte-identical timing behavior. Schedule: 3 silent retries at
cumulative +15s / +45s / +90s (comfortably longer than the ~60s Supabase reboot in SU-464934),
persisted in `sessionStorage` because Next may remount the boundary on every `reset()` call — a
plain `useState` counter would silently reset to 0 on every attempt and retry forever. During
retries the boundary shows only the same spinner pattern already used elsewhere in the app
(`AuctionsLayout`'s own loading spinner) plus a `sr-only` status — no error text, no stack trace.
After 3 failed attempts it shows a calm, blame-free message with a manual Retry button.
`app/not-found.tsx` reuses the identical visual language (same card-free centered message +
primary button) with no retry logic, since a 404 is a routine wrong URL, not a system fault.

## §3 — Shared EmptyState + named filters

`components/ui/empty-state.tsx` — one component, two props (`message`, `action: {label, onClick}`).
Wired into every place a filtered list can legitimately return zero rows:
- `components/auctions/AuctionSidebarList.tsx` + `components/auctions/AuctionTable.tsx` (radar's
  county/sale-type/day filters) — message and "Clear filters" handler built once in
  `AuctionsLayout.tsx` and passed down, so both views name the same active filter identically.
- `components/d4d/D4DBuildTab.tsx` (county + sale-date-range filter) — names the county and, if a
  date range is active, offers "Clear date range"; if no date range is set, offers "Try another
  county" (resets to Brevard) since that is the only widening move left.
- `components/discovery/DiscoveryPage.tsx` — names the search term/county/sale-type combination
  that returned nothing, action clears the search.

`app/counties/page.tsx`'s existing zero-result branch ("County coverage is temporarily
unavailable...") was deliberately **left untouched** — that page has no filter UI, so a
zero-row result there means the coverage RPC failed, not that a legitimate filter narrowed
things to nothing. Converting it to `EmptyState` would require inventing a widening action that
does not exist, which the brief explicitly prohibits ("never a bare 'No results'" implies the
action must be real, not invented). **BLOCKED as out of scope, not a gap** — documented rather
than silently skipped.

## §4 — Motion: shimmer disabled under prefers-reduced-motion

The app already had one global rule collapsing every animation/transition to near-zero duration
under `prefers-reduced-motion: reduce` (`app/globals.css` — `*, *::before, *::after {
animation-duration: 0.01ms !important; ... }`), and the existing codebase convention for
individual animated elements is `animate-pulse ... motion-reduce:animate-none` (e.g.
`components/deed/DeedThread.tsx`, `components/deed-home/ThreadView.tsx`). `components/ui/
skeleton.tsx` got the same one-class addition (`motion-reduce:animate-none`) rather than a new
shimmer with bespoke timing — **INFERRED**: the brief's "must use those durations [0.15s/0.2s],
that curve [cubic-bezier(0.4,0,0.2,1)]" reads as "stay inside the app's one motion system," and
that system's own convention for a decorative loading pulse is the existing global rule +
`motion-reduce:` variant, not a bespoke sub-200ms shimmer loop (which would strobe, not pulse).
No new easing/duration values were introduced anywhere.

### Negative test 3 — reduced motion disables the shimmer

Headless Chromium, `reducedMotion: 'reduce'` vs `'no-preference'` browser contexts, `/counties`
throttled to ~300kbps/400ms latency so the `loading.tsx` skeleton is still on screen when sampled,
`getComputedStyle` on the first `.animate-pulse` element:

```json
{
  "normal":  { "found": true, "animationName": "pulse", "animationDuration": "2s",     "animationIterationCount": "infinite" },
  "reduced": { "found": true, "animationName": "none",  "animationDuration": "1e-05s", "animationIterationCount": "1" }
}
```

Under reduced motion the animation is fully disabled (`animation-name: none`, duration collapses
to 0.01ms, runs once) — captured against the dev server (Turbopack) because the production build's
server-side `fetchCounties()` resolves fast enough that the Suspense fallback can race past a
throttled browser sample before it paints; the CSS mechanism under test (`globals.css`'s
`prefers-reduced-motion` rule + the `motion-reduce:` Tailwind variant) is identical, unbuilt-per-
environment CSS shipped in both dev and production — **VERIFIED** behavior, not environment-specific.
